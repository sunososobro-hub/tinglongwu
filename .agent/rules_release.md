# tlwu agent rules: release lane

Release-only rules, moved verbatim from `.agent/tlwu_rules.md` (#1856 part 1); section numbers are kept so every "section 11" / "section 14 <subsection>" citation still points here. Read by R-hard, R-merge, S-merge and S-hard (mergers / bump role / patrol) after the core file; workers (W-hard, slots A/B/C) need only the core. The core file's precedence statement covers this file too. Shared definitions (Allowed review authors, Opus PASS, dev Green, Ready, gates g1-g7, Protected paths, Outside PRs) stay in the core section 14.

## 11. Docs fast lane to main (owner 2026-11-13)
Owner: "Important things can't wait for a release." Docs-only changes may go to `main` without a release.
- Scope: the PR changes only `README*.md` and `docs/**/*.md` (not `docs/support.json`, no code, scripts, `.github/`, `.agent/`, packaging, `pyproject.toml`, `tinglongwu/__init__.py`).
- Order: the change is merged to `dev` first. Then a merger opens a PR `main <- docs/fastlane-N` that carries the same file contents (cherry-pick of the dev commit), title `docs(fastlane): ...`, body `Refs #N` + `tlwu-usage` line.
- Gate: `test` green on that PR and the diff stays inside the scope above (a merger checks `pulls/N/files`). Merge by rebase. No tag, no release; `release.yml` publishes nothing for a non-release push.
- Sync back: right after the fast-lane merge, merge `main` into `dev` (PR `dev <- main`, merge commit, auto-merge on green) so the next `release: vX.Y.Z` PR has no conflict.
- Not during a release: skip while a `release.yml` run on `main` is in progress; retry after it finishes. An open `release/vX.Y.Z` PR is no reason to wait (a fast-lane commit on `main` does not touch the snapshot).
- This is the only exception to "never touch main" in section 3; it does not allow `.github/` or code changes on `main`.

## 14. Auto-release safety, release parts (owner 2026-11-13, #588)
Owner: when ci, e2e, windows-build and hw-tests are all green on the release PR (now `release/vX.Y.Z -> main`, section 17 and "Release snapshot"; REQUIRED_CHECKS also has `audio-routing` and `install-clean`), release with no human click. That turns every merged dev change into a user-facing release, so these rules are hard stops for every merger (R-merge, S-merge, R-hard) and win over section 3 where they are stricter. The owner never merges PRs, including the release PR.
- Start: the release-PR rule in "Base", "Release snapshot" and "Kill switch" take effect only once `.github/workflows/auto-release.yml` exists on `dev` (#589); every other rule in this section applies now.

### Release PR green and per-platform lanes
- For the release PR, green also requires every REQUIRED_CHECKS workflow (`ci`, `e2e`, `windows-build`, `hw-tests`, `audio-routing`, `install-clean`) to be `success` on its head commit, the snapshot head (`skipped` does not count there). Exception (owner decision 2026-11-14, #848): when the `hw-tests` run for that head has not started (no runner picked it up) within `HW_RUNNER_WAIT_MIN` = 30 minutes, `hw-tests` is deferred: `ci`, `e2e`, `windows-build`, `audio-routing` and `install-clean` `success` are enough, the release notes say "hardware checks deferred", and a later `hw-tests` failure on that commit or the next dev push opens a P0 issue `[release] deferred hw-tests failed on vX.Y.Z`. A started `hw-tests` run is never deferred.
- Per-platform lanes (owner 2026-11-19, #1596: "mac壞了不影響 windows"): the release gate is the shared checks (ci `test` + offline suite) plus the Windows jobs. In `e2e` and `install-clean` a failed macOS / Linux job (by job name, `scripts/release_notes.py` `job_platform`) does not block the tag, the Windows exe or Windows auto-update. macOS / Linux ship by moving their marker tag (`mac-ok` / `linux-ok`) to the release tag only when all of that platform's jobs passed on the snapshot head (`release.yml`, after tagging); otherwise they stay on their last good version. `mac_install.sh` / `install.sh` and the menu's auto-update install that marker, not `main`. The release notes list per platform `shipped vX.Y.Z` or `skipped (not verified), stays on vA.B.C`. Only `release.yml` moves the marker tags. Android lane unchanged.

### Base (release PR)
- The release PR (`release/vX.Y.Z -> main`, or the legacy `dev -> main` during the transition; title `release: vX.Y.Z`) is merged only by `auto-release.yml`. Mergers and workers never merge, approve, close or edit it.

### Version bumps
- Only the bump role may change `__version__` in `tinglongwu/__init__.py`. The bump role is R-hard; it opens one PR titled `release: bump __version__ to X.Y.Z` with the gate evidence in the body.
- Cadence (owner 2026-11-14: "到啥就 release 啥，大功能才進版"; twice a day since owner 2026-11-16 18:22, #1274; was 1 h): every R-hard wake (scheduled or dispatched) opens a patch bump when all hold: the tag `v<dev __version__>` exists; dev is ahead of main by >= 1 merged PR; the `ci` `test` check on the dev tip is green; no open bump PR; no `hotfix.yml` run in progress and no open Hotfix lane back-merge PR (below: until it merges, dev's `__version__` is behind the hotfix tag and a bump would pick an already-released version); and this is R-hard's first wake after 11:00 or after 17:00 Asia/Taipei with no bump since that time (two releases a day; the owner pulls `dev` for anything sooner), or a P0/P1 bug fix merged since the last release. The bump needs an issue `[release] bump __version__ to X.Y.Z` and head `fix/<that issue>` (section 2). When its diff is only the `__version__` line (`X.Y.Z -> X.Y.(Z+1)`), optionally plus one new filled `## vX.Y.(Z+1)` section added to `docs/whats_new.md` (no other line of that file changed; #1267, so the snapshot is cut at the bump commit itself), it needs no Opus PASS: mergers merge it as soon as `test` is green (owner 2026-11-16; the release snapshot gates are the quality check). Mergers check it with `python scripts/release_notes.py bump-check --pr N` (exit 0 = no Opus needed) and merge with the printed `at <sha>` as the expected head. Any other file in a bump PR still needs an Opus PASS from another Opus run, never the one that opened it.
- The bump role may only make patch bumps (`X.Y.Z -> X.Y.(Z+1)`). Minor and major bumps are owner-only: the owner says so in an issue comment, and R-hard then opens the PR.
- Any other PR that touches `__version__` is a hard stop: add `needs-owner`, do not merge. The one exception is the Hotfix lane back-merge PR (below).

### Release snapshot (replaces the release freeze, #976 / #953)
- No freeze on dev: mergers keep merging ready PRs into `dev` while a release is under way. `release-fix` is no longer needed for that.
- Snapshot: when `ci` passes on a dev push and dev's `__version__` X.Y.Z has no tag `vX.Y.Z`, is newer than every tag and its bump commit is not on `main`, `release-pr.yml` creates the branch `release/vX.Y.Z` at the dev commit that set `__version__` (the bump), dispatches `e2e`, `audio-routing`, `hw-tests` and `install-clean` on it (their concurrency groups are per ref, so dev pushes never cancel them; `ci` and `windows-build` come from that commit's dev push, which is never cancelled) and opens the release PR `release/vX.Y.Z -> main`, title `release: vX.Y.Z`. Later dev pushes never move the snapshot.
- Gates on the snapshot head: every `scripts/release_notes.py` REQUIRED_CHECKS workflow (`ci`, `e2e`, `windows-build`, `hw-tests`, `audio-routing`, `install-clean`) `success` on the PR head (newest run per workflow), plus the #848 hw-tests deferral, the kill switch and a filled `docs/whats_new.md` section at that head. `auto-release.yml` merges it and `release.yml` `plan` re-checks the same gates on the snapshot head of the merged PR. Gates are never lowered.
- A red check on the snapshot: re-run that run (`gh run rerun <id> --failed`) for a flake, or dispatch the workflow on the snapshot ref (`gh workflow run e2e.yml --ref release/vX.Y.Z`). A real bug: fix it on `dev`, then R-hard opens the next patch bump; release-pr.yml then closes the old snapshot PR (superseded) and cuts `release/vX.Y.(Z+1)`. The snapshot never gets new commits.
- If `release-pr.yml` cannot create the branch (its job fails and prints the command; the workflow token may be refused a ref whose workflows differ from `main`), R-hard creates it with the printed `git push origin <sha>:refs/heads/release/vX.Y.Z` and runs `gh workflow run release-pr.yml --ref dev -f dry_run=false`. Nobody else creates, pushes to or deletes `release/v*` branches (other `release/*` names are ignored by the lane); `release-pr.yml` deletes them once the tag exists or the version is superseded, and `stale-branches` never touches them.
- A dev bump that is reverted or superseded (dev's `__version__` changes while a release PR is open): `release-pr.yml` closes that PR with a comment and deletes its branch. Until it does, `auto-release.yml` refuses a snapshot whose version is not dev's current `__version__`. Revert: on the owner's issue comment, R-hard opens a `release: revert __version__ to X.Y.Z` PR (green CI + an Opus PASS like any bump).
- Sync: the release merges into `main` with a merge commit whose second parent is the snapshot (a dev commit), so dev needs no merge back for it; section 11 fast-lane commits on `main` still get merged back to `dev`.
- Transition (until one release carries the new `release-pr.yml` / `auto-release.yml` to `main`): the old `release-pr.yml` on `main` still opens a legacy `dev -> main` release PR. While that legacy PR is open for dev's `__version__` and its tag does not exist, the old freeze holds for it alone: mergers merge into `dev` only PRs whose body says `release-fix` (`freeze-guard` enforces it, `scripts/release_freeze.py`). A `release/vX.Y.Z` PR never freezes anything.
- If a failed `release.yml` / `auto-release.yml` run already created the tag, re-run `release.yml` (not `auto-release.yml`, which rejects a version whose tag exists): a re-run at the same commit passes the tag check, because the tag points at that commit. If the failure is in the code at that commit, R-hard instead opens a patch bump (`X.Y.Z -> X.Y.(Z+1)`) PR whose body says `release-fix`; the corrective code change must be in that PR or already merged to `dev`, so the patch release never ships the faulty code unchanged.
- A release PR open for more than 24 h -> S-hard opens a P0 `[release] release stuck` issue.

### Hotfix lane (#950, #959)
- `hotfix.yml` (workflow_dispatch) ships one urgent fix as a patch release without the cadence lane: it branches `hotfix/vX.Y.(Z+1)` from the latest release tag, cherry-picks the fix, sets `__version__`, builds and tests once, publishes those same tested artifacts, tags the release and opens a back-merge PR `hotfix/vX.Y.Z -> dev`. It is the only release path besides the cadence lane (release PR + `auto-release.yml`); it is not a version bump PR and does not change the bump cadence above.
- Who: only R-hard or the integrator dispatches it. Mergers, workers and S-hard never dispatch it.
- When: only for an open or just-closed P0/P1 `bug` issue whose fix is already merged on `dev` (the dispatch input names that merged commit or PR). Never for features, `maint`, `infra` or unmerged code.
- Never during a release freeze (above), and never while a `release.yml`, `auto-release.yml` or another `hotfix.yml` run is in progress (the freeze ends when the release PR merges, before its tag exists; a hotfix then could pick the same `vX.Y.(Z+1)`): the hotfix waits until all are over (one hotfix at a time; `hotfix.yml` enforces it with a concurrency group, #957). Also not when an open bump PR exists, or dev's `__version__` has no tag yet (a bump merged but not released): finish or wait for that release instead (`scripts/hotfix_plan.py` refuses the same cases, #956). The kill switch (below) applies to it as to `auto-release.yml`.
- Back-merge: the `hotfix/vX.Y.Z -> dev` PR is the second allowed non-`fix/N` head (section 2; mergers do not add `needs-opus` for its head name). It merges on green CI (section 14 "Green") as a merge commit (not squash or rebase), so the release tag stays reachable from `dev`. Its files are the cherry-picked fix (already on `dev`) and `__version__`; it is the one PR besides the bump role's that may change `__version__` (Version bumps above). Any other file in it is a hard stop (`needs-opus`). Opus gate: the `__version__` change alone needs no Opus PASS; when the cherry-picked fix itself touches a protected or g4 path (e.g. `hotfix.yml`), the back-merge needs an Opus PASS like any PR touching that path.
- `hotfix.yml` itself is release-critical and a protected path: a PR that changes it merges only after an Opus PASS.

### Kill switch
- Auto-release runs only when the repo variable `AUTO_RELEASE` is `true` AND throttle #574 is at level 1 or above. `AUTO_RELEASE` missing or not `true`, or throttle level 0, stops it.
