# Releasing: Step 4: publish (release.yml)

Part of [RELEASING](../RELEASING.md).

4. **Publish.** `release.yml` runs on that dispatch (or on the push to `main` when someone merges by hand):
   - `plan` publishes only for a merged `release/vX.Y.Z` -> `main` PR (or the legacy `dev` -> `main` one) whose title starts with `release:` and names `v<__version__>`, newer than every tag (or an existing tag at this very commit, for a re-run), and only when every `REQUIRED_CHECKS` workflow is green on the PR's head commit (the snapshot head). `workflow_dispatch` with `publish=true` on `main` gets exactly these checks; any other dispatch is a dry run. Any other push to `main` publishes nothing, and pushing a plain `vX.Y.Z` tag by hand releases nothing (a pre-release tag is the one exception, see below).
   - `windows` builds the slim core zip on `windows-latest` with `build_windows.py --core` (#762: CPU llama, no `cuda_libs/`; #923: two layers. The runtime layer = Python + third-party packages + the `tlwu.exe` launcher, restored from the cache it shares with `windows-build.yml` and rebuilt only when `requirements/*.txt` or the packaging code change, in a packaging venv the script makes itself with `requirements/requirements-llama-cpu.txt`; the app layer = `tinglongwu/`, `tlwu_app/`, `tinglongwu_setup/`, repacked every time). `scripts/release_check.py` gates the core budget first (zip <= `MAX_CORE_MB` = 300 MB, no CUDA files), then `release/packaging/release_check.py` runs on the zip: size < 2 GiB (the per-asset limit), `check_dist_dlls.py`, the llama CPU-instruction check (every bundled `ggml-cpu*.dll` must stay within the AVX2 baseline: no AVX-512 / AVX-VNNI / AMX, #74), `tlwu.exe --smoke` and `tlwu.exe --selftest` (CPU, whisper tiny + Hy-MT2; setup downloads both first). Any failure stops the release before anything is uploaded. The last step writes the job time into the summary and warns (never fails) when it is over `CORE_JOB_BUDGET_MIN` = 20 min. The GPU libraries are not in this zip; they ship as a separate GPU pack (#740).
   - `gpu-pack` (#764) runs in parallel with `windows` (it needs only `plan`, so it is never on the critical path): a venv with `requirements/requirements-llama-cuda.txt` and the CUDA 12 wheels (`requirements/requirements-gpu.txt` + nvrtc), then `build_windows.py --gpu-pack-only` (#763, no Nuitka) writes `tinglongwu-gpu-pack.zip` and `tinglongwu-gpu-pack.zip.manifest.json`, whose url names this release's tag. `scripts/release_check.py --gpu-pack <zip> --tag <tag>` checks that the zip matches its manifest (size, sha256), holds `ggml-cuda.dll` and the CUDA DLLs it imports, stays under 2 GiB, and belongs to the same tag (same version) as the core zip; it writes the pack size to the job summary.
   - `release` waits for both `windows` and `gpu-pack`, re-checks the GPU pack after the artifact download, tags the merge commit (it refuses a tag that already points elsewhere) and creates a **draft** release with `tinglongwu-win64.zip`, `tinglongwu-gpu-pack.zip` + its manifest, the install scripts with the tag embedded (placeholder `__TLWU_REF__`), `SHA256SUMS.txt` (core zip, GPU pack, manifest and scripts; `sha256sum -c` runs on it) and the notes: Download, the support/contributors block, What's new, the check table with the zip SHA256, the GPU line, changes and thanks. Its last step writes `release wall time: N min` (first job start -> release created) to the summary and warns (never fails) when it is over `RELEASE_BUDGET_MIN` = 20 min.
   - `windows-installer` builds the setup wizard with Inno Setup, attaches it as `tinglongwu-setup-X.Y.Z.exe` and as the fixed name `tinglongwu-setup.exe`, adds both hashes to `SHA256SUMS.txt`, then publishes the draft, which becomes `latest` (a suffix version such as `1.2.3-beta.1` is published as a pre-release and does not). It publishes only when the notes contain no `TODO:`: What's new comes from `docs/whats_new.md` (`## vX.Y.Z`), else from an edited `## What's new` in the release PR body; with neither the TODO line stays and the release stays a draft. If a job fails, the release stays a draft and the README keeps pointing at the previous one; re-run the workflow.
