# Releasing

Branches: `main` is stable (users and auto-update follow it); `dev` is where daily work happens. `main` is protected: changes arrive by pull request with the `test` CI check green.

Releases are automatic (#589, owner decision 2026-11-13; rules: `.agent/tlwu_rules.md` section 14). Nobody clicks merge.

1. **Bump.** The bump role (R-hard) opens one PR to `dev` titled `release: bump __version__ to X.Y.Z` (patch bumps only; minor and major only on the owner's word). It carries `tinglongwu/__init__.py` `__version__` (the single source, #462), a new `## vX.Y.Z` section on top of `docs/whats_new.md` (at most 3 plain-language bullets about what users notice, no PR numbers, no `TODO`), `docs/support.json`, `.all-contributorsrc` and the `python scripts/render_support.py` output (step 4). Agents may keep or downgrade lights; only hw-tests evidence justifies a green Windows/NVIDIA light.
2. **Release PR.** When `ci` passes on a push to `dev`, `release-pr.yml` opens or updates the single `dev` -> `main` PR titled `release: vX.Y.Z`. Its body has `## What's new` (from `docs/whats_new.md`; a `- TODO:` line until the bump PR wrote the section), the merged PRs since the last tag and thanks to every non-owner, non-bot author of a PR or issue (links, no @mentions). If tag `vX.Y.Z` already exists, the body says to bump `__version__` first.
3. **Auto-merge.** `auto-release.yml` runs after every `ci`, `e2e`, `windows-build` or `hw-tests` run on `dev` completes (`scripts/release_notes.py auto`). It merges the release PR only when all of these hold, else it writes the reason into its job summary and does nothing:
   - kill switch: the repo variable `AUTO_RELEASE` is `true` and the throttle issue #574 reads `level: 1` or higher (unreadable = stop);
   - the open release PR is from this repo and its head is the commit that run was for;
   - its title is `release: v<__version__>` and that version is newer than every tag (a version bump is the only trigger);
   - `ci`, `e2e`, `windows-build` and `hw-tests` all concluded `success` on the head (`skipped` does not count). `hw-tests` runs on the maintainer's self-hosted NVIDIA runner, so it is the GPU evidence;
   - `docs/whats_new.md` has a filled `## vX.Y.Z` section.

   Then `gh pr merge --merge --match-head-commit <head>` with the workflow token (a merge commit, never squash; never `--auto`, which waits only for `test`), and `gh workflow run release.yml --ref main -f publish=true`, because a merge by the workflow token fires no `push`.
4. **Publish.** `release.yml` runs on that dispatch (or on the push to `main` when someone merges by hand):
   - `plan` publishes only for a merged `dev` -> `main` PR whose title starts with `release:` and names `v<__version__>`, newer than every tag (or an existing tag at this very commit, for a re-run), and only when the four checks are green on the PR's head commit. `workflow_dispatch` with `publish=true` on `main` gets exactly these checks; any other dispatch is a dry run. Any other push to `main` publishes nothing, and pushing a plain `vX.Y.Z` tag by hand releases nothing (a pre-release tag is the one exception, see below).
   - `windows` builds the CUDA package on `windows-latest` with `build_windows.py --allow-cpu-only` (the runner has no NVIDIA driver, so the smoke may use the CPU llama fallback), then `packaging/release_check.py` on the zip: size < 2 GiB (the per-asset limit), `check_dist_dlls.py`, the llama CPU-instruction check (every bundled `ggml-cpu*.dll` must stay within the AVX2 baseline: no AVX-512 / AVX-VNNI / AMX, #74), `tlwu.exe --smoke` and `tlwu.exe --selftest` (CPU, whisper tiny + Hy-MT2; setup downloads both first). Any failure stops the release before anything is uploaded.
   - `release` tags the merge commit (it refuses a tag that already points elsewhere) and creates a **draft** release with `tinglongwu-win64.zip`, the install scripts with the tag embedded (placeholder `__TLWU_REF__`), `SHA256SUMS.txt` (zip + scripts) and the notes: Download, the support/contributors block, What's new, the check table with the zip SHA256, the GPU line, changes and thanks.
   - `windows-installer` builds the setup wizard with Inno Setup, attaches it as `tinglongwu-setup-X.Y.Z.exe` and as the fixed name `tinglongwu-setup.exe`, adds both hashes to `SHA256SUMS.txt`, then publishes the draft, which becomes `latest` (a suffix version such as `1.2.3-beta.1` is published as a pre-release and does not). It publishes only when the notes contain no `TODO:`: What's new comes from `docs/whats_new.md` (`## vX.Y.Z`), else from an edited `## What's new` in the release PR body; with neither the TODO line stays and the release stays a draft. If a job fails, the release stays a draft and the README keeps pointing at the previous one; re-run the workflow.
5. Dry runs publish nothing: `gh workflow run release.yml --ref <branch>` (build, every check, notes in the job summary) and `gh workflow run release-pr.yml --ref <branch> -f dry_run=true` (the PR title and body in the summary).

   **Rollback** of a bad release `vBAD`: `gh release edit vBAD --prerelease` (the one exception to the #478 rule below: `releases/latest` falls back to the previous stable release), revert the bad change on `dev`, and let the bump role ship a patch bump; that release becomes `latest`. Never delete a published tag or rewrite its assets.

   **Owner one-time actions** (agents do not do these): (1) one manual `dev` -> `main` release so `main` carries `auto-release.yml`, the new `release.yml` and `release-pr.yml` (`workflow_run` and `workflow_dispatch` use the copies on `main`); (2) turn on `enforce_admins` for `main`; (3) set the repo variable `AUTO_RELEASE=true` (Settings > Secrets and variables > Actions > Variables); (4) Settings > Actions > General > "Allow GitHub Actions to create and approve pull requests"; (5) later, a tag ruleset so only Actions can create `v*` tags. To stop releases at once: set `AUTO_RELEASE` to anything but `true`, or the throttle #574 to `level: 0`.

   Without "Allow GitHub Actions to create and approve pull requests" `release-pr.yml` only writes the PR into its summary and fails. A PR created with the workflow token starts no `pull_request` runs, but its head is the `dev` commit whose push runs already reported `test`, so the required check on `main` is satisfied. `release-pr.yml` runs from the default branch's copy (`workflow_run`), so it starts working once it is on `main`.

   The README install table links `releases/latest/download/{tinglongwu-setup.exe,mac_install.sh,install.sh}`, so it installs from the newest release that is **not** marked pre-release. The raw `main` scripts fall back to `main` when the ref placeholder is not embedded; do not link them for end users.

   Pre-release from `dev` (#112): set `__version__` to `X.Y.Z-suffix` (for example `1.2.3-beta.1`) on `dev`, wait for `ci`, `e2e`, `windows-build` and `hw-tests` to pass on that commit, then push the tag `vX.Y.Z-suffix` at it. `release.yml` runs on `v*-*` tags: `plan` checks the tag is on `main` or `dev` (a plain `vX.Y.Z` must be on `main` and only comes from the release PR; a hand-pushed plain tag starts nothing), that it equals `v<__version__>` and that the four checks are green on the tagged commit, then the same `windows`, `release` and `windows-installer` jobs publish it marked pre-release, so it never becomes `latest`. `tests/test_release_branch_check.py` runs the branch check against sample tags.

   Release policy (owner decision in #478, amends #345): a plain `vX.Y.Z` tag is a normal release even while the version is 0.x, so the newest 0.x release stays `latest` and the README install links keep working. Do not add `--prerelease` for 0.x tags and do not re-flag published 0.x releases as pre-release: `releases/latest/download/*` skips pre-releases, so every install link would 404. Only a tag with a suffix (`-beta.1`, `-rc.1`) is a pre-release. `tests/test_release_prerelease_rule.py` runs the workflow's rule against sample tags.

6. Before the bump, update the single source of the support tables and the contributors block: `docs/support.json` (lights, legend, download hints) and `.all-contributorsrc` (people). Run `python scripts/render_support.py` to rewrite the contributors row (`<!-- CONTRIBUTORS:START -->` ... `<!-- CONTRIBUTORS:END -->`) in the three READMEs and the dot grid on the roadmap page; CI fails (`tests/test_render_support.py`) if they differ from the source. The support tables appear only in the release notes and on the roadmap. Rules for the source:

   - Device table: only mark 🟢 what someone ran on a real machine (or in the release gate) for this release.
   - Language table: rows are languages by native name plus code (`中文 (zh)`, `English (en)`, `日本語 (ja)`, `Русский (ru)`, `한국어 (ko)`), no flag emoji anywhere (flags map languages to countries). Chinese is one row (speech has no script); Traditional and Simplified are output columns. If a light holds on one OS only, say so in the cell (`🟢 Windows`). Only list languages this tag supports.
   - Contributors: all-time and cumulative (reporters included; the list only grows). "N people" counts humans only; AI tools get their own line, as text links, no logos. The block has no `@` text: an @mention notifies the person, so mentioning everyone on every release is spam.

7. The notes start from `python scripts/render_support.py --notes vX.Y.Z` (`## Download`, the support tables and contributors block, `## What's new`); `scripts/release_notes.py notes` fills What's new from `docs/whats_new.md` (else the release PR). `windows-installer` publishes only when the notes contain no `TODO:`. To edit a published or draft release later:

   - `## What's new`: at most 3 plain-language bullets about what the user notices. No PR or issue numbers.
   - Below it, `<details><summary>For developers</summary>`: the full changelog with PR/issue links, the evidence for each light in the tables, every asset with its SHA-256, test and gate notes, known issues, a `Thanks` line that @mentions only this release's new contributors (count a PR only if it is in this tag: `git merge-base --is-ancestor <merge-commit> vX.Y.Z`), and a "How to contribute" link to `CONTRIBUTING.md` and the `good first issue` label.
   - Do not hand-edit the block between the markers. To change it, edit the source and run `python scripts/render_support.py --edit vX.Y.Z` (it fetches the notes with gh, swaps the block and uploads them; no shell redirection, so no PowerShell encoding issues).
   - Then publish: `gh release edit vX.Y.Z --draft=false`, but only for a draft that `windows-installer` finished (both `tinglongwu-setup*.exe` files attached). If that job failed, re-run the workflow instead: publishing a draft without the wizard makes it `latest` and breaks the README Windows link.

If the workflow fails before the release is published, re-run it: the draft only has its files replaced, and the wizard lines in `SHA256SUMS.txt` are rewritten, not appended. The workflow refuses to touch a release that is already published. The zip comes from the workflow; do not replace it by hand. A version with a suffix (`__version__ = "1.2.3-beta.1"`) gives a pre-release. If the tag itself is wrong (for example a pre-release tag on neither `main` nor `dev`), delete the draft release (`gh release delete vX.Y.Z`) and the tag (`git push origin :refs/tags/vX.Y.Z`), fix `__version__` on dev, and merge the release PR again (or, for a pre-release, push the tag again).
