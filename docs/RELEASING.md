# Releasing

Branches: `main` is stable (users and auto-update follow it); `dev` is where daily work happens. `main` is protected: changes arrive by pull request with the `test` CI check green.

Releases are automatic (#589, owner decision 2026-11-13; rules: `.agent/tlwu_rules.md` sections 14 and 17). Nobody clicks merge.

Two lanes (#976, owner 2026-11-15): `dev` is the fast lane (a PR merges on `test` alone; `dev-build.yml` publishes every dev push as the rolling `dev-latest` pre-release), `main` is the quality lane. A release is cut from a snapshot branch `release/vX.Y.Z` that points at the dev commit of the version bump (or, when the bump had no `## vX.Y.Z` section in `docs/whats_new.md`, the first later dev commit that adds it; until then nothing is cut and the plan says "waiting for whats_new section", #1012), so later merges to `dev` never restart, cancel or freeze it, and every release gate runs on that snapshot.

1. **Bump.** The bump role (R-hard) opens one PR to `dev` titled `release: bump __version__ to X.Y.Z` (patch bumps only; minor and major only on the owner's word). It carries `tinglongwu/__init__.py` `__version__` (the single source, #462), a new `## vX.Y.Z` section on top of `docs/whats_new.md` (at most 3 plain-language bullets about what users notice, no PR numbers, no `TODO`). Support updates (`docs/support.json`, `.all-contributorsrc` and the `python scripts/render_support.py` output) land before the bump in their own PR (step 6), so the bump stays exempt. Agents may keep or downgrade lights; only hw-tests evidence justifies a green Windows/NVIDIA light. A bump PR whose diff is only the `__version__` line plus that new `## vX.Y.Z` section merges on green `test` without an Opus PASS (`python scripts/release_notes.py bump-check --pr N` exits 0, #1267); any other file in it needs an Opus PASS.
2. **Snapshot and release PR.** When `ci` passes on a push to `dev` (the dev tip) and `__version__` X.Y.Z has no tag, is newer than every tag and its bump commit is not on `main` yet, `release-pr.yml` (`scripts/release_notes.py snapshot`):
   - creates `release/vX.Y.Z` at the dev commit that set `__version__` (once; later dev pushes never move it). If GitHub refuses the workflow token this ref, the job fails and prints `git push origin <sha>:refs/heads/release/vX.Y.Z && gh workflow run release-pr.yml --ref dev -f dry_run=false`, which R-hard runs;
   - dispatches `e2e`, `audio-routing`, `hw-tests` and `install-clean` on `release/vX.Y.Z` (skipping a workflow already green on that commit, and a `hw-tests` run already in progress). Their concurrency groups are per ref, so dev pushes cannot cancel these runs; `ci` and `windows-build` come from the commit's own dev push, which is never cancelled. Snapshot runs restore caches only from `main` or the snapshot ref, so the first e2e / audio-routing run of a snapshot downloads its models;
   - opens the PR `release/vX.Y.Z` -> `main` titled `release: vX.Y.Z`;
   - closes a release PR for another version (the bump was reverted or superseded) and deletes `release/v*` branches whose tag exists or that were superseded. `stale-branches` never deletes `release/v*`.

   Its body has `## What's new` (from `docs/whats_new.md`; a `- TODO:` line until the bump PR wrote the section), the merged PRs since the last tag and thanks to every non-owner, non-bot author of a PR or issue (links, no @mentions). The PR never changes after it is opened; the next version gets its own snapshot. A red check: re-run it, or `gh workflow run <workflow>.yml --ref release/vX.Y.Z`; a real bug is fixed on `dev` and shipped with the next patch bump (the old snapshot PR is then closed as superseded).

   Transition: `release-pr.yml` runs from `main`'s copy, so until one release carries this version to `main` the old copy opens a legacy `dev` -> `main` PR instead. The scripts accept both, and dev stays frozen (`freeze-guard`, `release-fix` only) for that legacy PR alone.
3. **Auto-merge.** `auto-release.yml` runs after every `ci`, `e2e`, `windows-build`, `hw-tests` or `audio-routing` run on `dev` or a `release/v*` ref completes, after `release-pr` and every 15 minutes (`scripts/release_notes.py auto`, run from the dev tip). It merges the release PR only when all of these hold, else it writes the reason into its job summary and does nothing:
   - kill switch: the repo variable `AUTO_RELEASE` is `true` and the throttle issue #574 reads `level: 1` or higher (unreadable = stop);
   - the open release PR is from this repo, its head is `release/<the title's version>` and that head is a dev commit (legacy `dev` -> `main` PR: its head is the commit that run was for);
   - its title is `release: v<__version__>` (read at the snapshot head) and that version is newer than every tag (a version bump is the only trigger);
   - every `REQUIRED_CHECKS` workflow (`ci`, `e2e`, `windows-build`, `hw-tests`, `audio-routing`, `install-clean`) concluded `success` on the head, newest run per workflow (`skipped` does not count). `hw-tests` runs on the maintainer's self-hosted NVIDIA runner, so it is the GPU evidence; if that runner is offline and the `hw-tests` run for the head has not started within `HW_RUNNER_WAIT_MIN` = 30 minutes (#848, `scripts/hw_deferral.py`), `hw-tests` is deferred: the gate merges on the other cloud checks (`ci`, `e2e`, `windows-build`, `audio-routing`, `install-clean`), marks the PR body so `release.yml` accepts it, the notes say "hardware checks deferred", and when `hw-tests` later fails on that commit or a newer dev push, the `deferred-hw-tests` job opens a P0 issue `[release] deferred hw-tests failed on vX.Y.Z`. A schedule re-runs the gate every 15 minutes, since a queued run completes nothing; `audio-routing` (#849) must be `success` too: on `windows-latest` it installs VB-CABLE (official zip, pinned SHA-256), checks that a tone played into "CABLE Input" is captured on "CABLE Output" (RMS above `SILENCE_RMS_THRESHOLD`, `scripts/cable_loopback_check.py`) and runs `speak_selftest.py` en/ru through the cable, so speak-mode routing no longer depends on the home PC; a deferral of `hw-tests` never drops it (it is in `CLOUD_CHECKS`);
   - `docs/whats_new.md` at the head has a filled `## vX.Y.Z` section.

   Then `gh pr merge --merge --match-head-commit <head>` with the workflow token (a merge commit, never squash; never `--auto`, which waits only for `test`), and `gh workflow run release.yml --ref main -f publish=true`, because a merge by the workflow token fires no `push`. The gate also runs after `release-pr.yml`, so a PR opened or retitled after the checks finished is not missed, and it never merges a version whose release PR was already merged. If the merge worked but the dispatch failed (the job says so), run `gh workflow run release.yml --ref main -f publish=true`: `plan` re-checks every gate.
4. **Publish.** `release.yml` runs on that dispatch (or on the push to `main` when someone merges by hand):
   - `plan` publishes only for a merged `release/vX.Y.Z` -> `main` PR (or the legacy `dev` -> `main` one) whose title starts with `release:` and names `v<__version__>`, newer than every tag (or an existing tag at this very commit, for a re-run), and only when every `REQUIRED_CHECKS` workflow is green on the PR's head commit (the snapshot head). `workflow_dispatch` with `publish=true` on `main` gets exactly these checks; any other dispatch is a dry run. Any other push to `main` publishes nothing, and pushing a plain `vX.Y.Z` tag by hand releases nothing (a pre-release tag is the one exception, see below).
   - `windows` builds the slim core zip on `windows-latest` with `build_windows.py --core` (#762: CPU llama, no `cuda_libs/`; #923: two layers. The runtime layer = Python + third-party packages + the `tlwu.exe` launcher, restored from the cache it shares with `windows-build.yml` and rebuilt only when `requirements/*.txt` or the packaging code change, in a packaging venv the script makes itself with `requirements/requirements-llama-cpu.txt`; the app layer = `tinglongwu/`, `tlwu_app/`, `tinglongwu_setup/`, repacked every time). `scripts/release_check.py` gates the core budget first (zip <= `MAX_CORE_MB` = 300 MB, no CUDA files), then `release/packaging/release_check.py` runs on the zip: size < 2 GiB (the per-asset limit), `check_dist_dlls.py`, the llama CPU-instruction check (every bundled `ggml-cpu*.dll` must stay within the AVX2 baseline: no AVX-512 / AVX-VNNI / AMX, #74), `tlwu.exe --smoke` and `tlwu.exe --selftest` (CPU, whisper tiny + Hy-MT2; setup downloads both first). Any failure stops the release before anything is uploaded. The last step writes the job time into the summary and warns (never fails) when it is over `CORE_JOB_BUDGET_MIN` = 20 min. The GPU libraries are not in this zip; they ship as a separate GPU pack (#740).
   - `gpu-pack` (#764) runs in parallel with `windows` (it needs only `plan`, so it is never on the critical path): a venv with `requirements/requirements-llama-cuda.txt` and the CUDA 12 wheels (`requirements/requirements-gpu.txt` + nvrtc), then `build_windows.py --gpu-pack-only` (#763, no Nuitka) writes `tinglongwu-gpu-pack.zip` and `tinglongwu-gpu-pack.zip.manifest.json`, whose url names this release's tag. `scripts/release_check.py --gpu-pack <zip> --tag <tag>` checks that the zip matches its manifest (size, sha256), holds `ggml-cuda.dll` and the CUDA DLLs it imports, stays under 2 GiB, and belongs to the same tag (same version) as the core zip; it writes the pack size to the job summary.
   - `release` waits for both `windows` and `gpu-pack`, re-checks the GPU pack after the artifact download, tags the merge commit (it refuses a tag that already points elsewhere) and creates a **draft** release with `tinglongwu-win64.zip`, `tinglongwu-gpu-pack.zip` + its manifest, the install scripts with the tag embedded (placeholder `__TLWU_REF__`), `SHA256SUMS.txt` (core zip, GPU pack, manifest and scripts; `sha256sum -c` runs on it) and the notes: Download, the support/contributors block, What's new, the check table with the zip SHA256, the GPU line, changes and thanks. Its last step writes `release wall time: N min` (first job start -> release created) to the summary and warns (never fails) when it is over `RELEASE_BUDGET_MIN` = 20 min.
   - `windows-installer` builds the setup wizard with Inno Setup, attaches it as `tinglongwu-setup-X.Y.Z.exe` and as the fixed name `tinglongwu-setup.exe`, adds both hashes to `SHA256SUMS.txt`, then publishes the draft, which becomes `latest` (a suffix version such as `1.2.3-beta.1` is published as a pre-release and does not). It publishes only when the notes contain no `TODO:`: What's new comes from `docs/whats_new.md` (`## vX.Y.Z`), else from an edited `## What's new` in the release PR body; with neither the TODO line stays and the release stays a draft. If a job fails, the release stays a draft and the README keeps pointing at the previous one; re-run the workflow.
5. Dry runs publish nothing: `gh workflow run release.yml --ref <branch>` (build, every check, notes in the job summary) and `gh workflow run release-pr.yml --ref <branch> -f dry_run=true` (the PR title and body in the summary).

   **Rollback** of a bad release `vBAD`: `gh release edit vBAD --prerelease` (the one exception to the #478 rule below: `releases/latest` falls back to the previous stable release), revert the bad change on `dev`, and let the bump role ship a patch bump; that release becomes `latest`. Never delete a published tag or rewrite its assets.

   **Owner one-time actions** (agents do not do these): (1) done: `main` carries `auto-release.yml`, `release.yml` and `release-pr.yml` (`workflow_run` and `schedule` use the copies on `main`; each release carries the newer copies there); (2) turn on `enforce_admins` for `main`; (3) set the repo variable `AUTO_RELEASE=true` (Settings > Secrets and variables > Actions > Variables); (4) Settings > Actions > General > "Allow GitHub Actions to create and approve pull requests"; (5) later, a tag ruleset so only Actions can create `v*` tags. To stop releases at once: set `AUTO_RELEASE` to anything but `true`, or the throttle #574 to `level: 0`.

   Without "Allow GitHub Actions to create and approve pull requests" `release-pr.yml` only writes the PR into its summary and fails. A PR created with the workflow token starts no `pull_request` runs, but its head is the dev commit whose push runs already reported `test`, so the required check on `main` is satisfied. `release-pr.yml` runs from the default branch's copy (`workflow_run`), so it starts working once it is on `main`.

   The README install table links `releases/latest/download/{tinglongwu-setup.exe,mac_install.sh,install.sh}`, so it installs from the newest release that is **not** marked pre-release. The raw `main` scripts fall back to `main` when the ref placeholder is not embedded; do not link them for end users.

   Pre-release from `dev` (#112): set `__version__` to `X.Y.Z-suffix` (for example `1.2.3-beta.1`) on `dev`, wait for `ci`, `e2e`, `windows-build` and `hw-tests` to pass on that commit, then push the tag `vX.Y.Z-suffix` at it. `release.yml` runs on `v*-*` tags: `plan` checks the tag is on `main` or `dev` (a plain `vX.Y.Z` must be on `main` and only comes from the release PR; a hand-pushed plain tag starts nothing), that it equals `v<__version__>` and that the four checks are green on the tagged commit, then the same `windows`, `release` and `windows-installer` jobs publish it marked pre-release, so it never becomes `latest`. `tests/test_release_branch_check.py` runs the branch check against sample tags.

   Release policy (owner decision in #478, amends #345): a plain `vX.Y.Z` tag is a normal release even while the version is 0.x, so the newest 0.x release stays `latest` and the README install links keep working. Do not add `--prerelease` for 0.x tags and do not re-flag published 0.x releases as pre-release: `releases/latest/download/*` skips pre-releases, so every install link would 404. Only a tag with a suffix (`-beta.1`, `-rc.1`) is a pre-release. `tests/test_release_prerelease_rule.py` runs the workflow's rule against sample tags.

6. Before the bump, update the single source of the support tables and the contributors block: `docs/support.json` (lights, legend, download hints) and `.all-contributorsrc` (people). Run `python scripts/render_support.py` to rewrite the contributors row (`<!-- CONTRIBUTORS:START -->` ... `<!-- CONTRIBUTORS:END -->`) in the three READMEs and the dot grid on the roadmap page; CI fails (`tests/test_render_support.py`) if they differ from the source. The support tables appear only in the release notes and on the roadmap. Rules for the source:

   - Device table: only mark 🟢 what someone ran on a real machine (or in the release gate) for this release.
   - Language table: rows are languages by native name plus code (`中文 (zh)`, `English (en)`, `日本語 (ja)`, `Русский (ru)`, `한국어 (ko)`), no flag emoji anywhere (flags map languages to countries). Chinese is one row (speech has no script); Traditional and Simplified are output columns. If a light holds on one OS only, say so in the cell (`🟢 Windows`). Only list languages this tag supports.
   - Contributors: all-time and cumulative (reporters included; the list only grows). "N people" counts humans only; AI tools get their own line, as text links, no logos. The block has no `@` text: an @mention notifies the person, so mentioning everyone on every release is spam.

7. The notes start from `python scripts/render_support.py --notes vX.Y.Z` (`## Download`, the support tables and contributors block, `## What's new`); `scripts/release_notes.py notes` fills What's new from `docs/whats_new.md` (else the release PR). `windows-installer` publishes only when the notes contain no `TODO:`. To edit a published or draft release later:

   - `## What's new`: at most 3 plain-language bullets about what the user notices. No PR or issue numbers.
   - Below it, `<details><summary>For developers</summary>`: the full changelog with PR/issue links, the evidence for each light in the tables, every asset with its SHA-256, test and gate notes, known issues, a `Thanks` line that @mentions only this release's new contributors (count a PR only if it is in this tag: `git merge-base --is-ancestor <merge-commit> vX.Y.Z`), and a "How to contribute" link to `.github/CONTRIBUTING.md` and the `good first issue` label.
   - Do not hand-edit the block between the markers. To change it, edit the source and run `python scripts/render_support.py --edit vX.Y.Z` (it fetches the notes with gh, swaps the block and uploads them; no shell redirection, so no PowerShell encoding issues).
   - Then publish: `gh release edit vX.Y.Z --draft=false`, but only for a draft that `windows-installer` finished (both `tinglongwu-setup*.exe` files attached). If that job failed, re-run the workflow instead: publishing a draft without the wizard makes it `latest` and breaks the README Windows link.

If the workflow fails before the release is published, re-run it: the draft only has its files replaced, and the wizard lines in `SHA256SUMS.txt` are rewritten, not appended. The workflow refuses to touch a release that is already published. The zip comes from the workflow; do not replace it by hand. A version with a suffix (`__version__ = "1.2.3-beta.1"`) gives a pre-release. If the tag itself is wrong (for example a pre-release tag on neither `main` nor `dev`), delete the draft release (`gh release delete vX.Y.Z`) and the tag (`git push origin :refs/tags/vX.Y.Z`), fix `__version__` on dev, and merge the release PR again (or, for a pre-release, push the tag again).
